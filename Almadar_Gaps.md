- **G-ORBITAL-CORE-002** — `EmbeddedKernel::frame` costs about 0.11 ms per ticking trait. On the iOS simulator (iPhone 17 Pro, release C-ABI lib from `make ios-lib`), a frame with 100 ticking traits takes p50 11.4 ms and with 1 000 takes p50 557 ms / p95 752 ms, so every one of 600 frames misses the 16.7 ms budget and the R1-device frame gate (2 ms) by about 280×. Dispatch is fine (p50 0.15 ms over 10^4 events). Suspects: the frame path in `runtime/kernel.rs` and `effects/executor.rs` (per-trait entity layering, per-tick response building, render-store work per tick). Fix: profile one frame (allocation count + time per stage, like `tests/dispatch_alloc_count.rs`), then cut per-trait work so cost grows with traits that actually change. `orbital-core` [architectural] — evidence: `@almadar-io/parity` device rows (`frame-60hz-100`, `frame-60hz-1000`), `orbital-shell-ios/tests/device-bench/`; prevention rung: none of the language rungs (performance), gated by the device frame row.
- **Close by deleting.** Remove the entry in the same commit as the fix.

- **G-ORBITAL-CORE-038** — The dispatch lane (`crates/runtime/src/kernel/lane.rs`) still lets an UNTOKENED call re-enter when it runs on the thread the RUNNING holder occupies. The parked refusal and the FIFO wait are keyed on an explicit `LaneTurn` (R-b1, 2026-10-21), and the kernel's own sub-dispatches carry the turn, but `orbital-server`'s `program/dispatch` substrate host (`ServerSubstrate::run`, `runtime.rs`) answers the ask in place with `dispatch_continuing`, and `SubstrateHandler::run(op, args)` hands it no turn to carry. It is sound (a running holder occupies its thread synchronously), but it is implicit. Fix: pass the asking dispatch's `LaneTurn` to the substrate/service host (`SubstrateHandler::run` or `ServiceCaller`), have `ServerSubstrate` call `dispatch_in_turn`, then delete the `in_place` clause from `DispatchLane::enter`. `orbital-core-runtime` + `orbital-server` [architectural] — prevention rung: none of the language rungs (host concurrency), gated by the `tests/cross_trait_dispatch.rs` lane pins and `orbital-server` `go_as` program/dispatch tests. R-b1 (2026-10-21): a host answering a parked dispatch's ask in place now carries its turn and is refused (`control_an_unkeyed_program_dispatch_on_behalf_of_a_parked_dispatch_is_refused_not_hung`); the retiring `orbital-server` still answers an unkeyed `program/dispatch` in place without the turn, so it waits on its own parked dispatch (its three `program/dispatch` tests are `#[ignore]`d, covered by the core tests).

- **G-ORBITAL-CORE-040** — A keyed, routed `call-service` is still answered in place on a host with a completion sink, so its asking dispatch holds the lane until the service answers; the R-a rule (keyed routed asks defer, the answer runs as a dispatch of its own and `cancel-call` reaches it in flight) covers it, and the owner scoped it out of the 2026-10-21 round. Deferring it needs the answering host to own its service handler: `BlockingHost.service` is a borrowed `&dyn ServiceHandler`, which cannot move to the worker thread `Completions::defer_substrate`/`run_later` spawn (keyed substrate ops defer that way since R-b1), so the host needs an `Arc<dyn ServiceHandler>` (`'static`) and a `cancel-call` that cancels the live key. The native server serves no services at all (`NativeHost` answers every call with `NoProviders`). `orbital-core-runtime` (`resumable.rs` `BlockingHost`, `native_host.rs`) [architectural] — prevention rung: none of the language rungs (host concurrency); regression gate: a twin of `a_keyed_program_dispatch_runs_after_the_asking_dispatch_commits_and_its_completion_after_it` for `call-service`, plus a cancel-in-flight test.
- **G-ORBITAL-CORE-039** — Owner call: whether keyed `os/*` completions on a blocking host count toward `CROSS_TRAIT_CASCADE_CAP` (2000 steps, `crates/runtime/src/kernel.rs`). On the `orb <command>` program host every completion runs inside the one inbound dispatch, so a `cli` program like `std-orb-census` that walks a large tree in one dispatch is cut at 2000 steps. The cut no longer hangs: since 2026-10-21 (lane RE) the cap site records a `CascadeCut` on the outcome and the inbound answer is a 500 `cascade-cap` naming the cap, trait and event (`kernel/inbound.rs` `inbound_cut`, pinned by `a_handler_cut_by_the_cascade_cap_answers_the_cut`), so `orb <command>` exits 1. What stays open: a program whose work is legitimately longer than the cap still cannot finish. `orbital-core-runtime` [owner-decision] — prevention rung: none of the language rungs (a host run-loop budget, not a program defect).

- **G-ORBITAL-CORE-043** — Plain `os/stdin-read` is documented and typed as one bounded `{ data: bytes, eof: boolean }` read, and `os_host/process.rs::stdin_read` implements it, but `kernel.rs::run_os` rejects it as an unkeyed stream before reaching the host. Keyed reads also stream without an explicit `onMessage`, contradicting the documented single-read variant and preventing bounded asynchronous ACK-driven reads. Reproduction: native `orb execute --steps` of INPUT_START in `std-stdio-lines` emits `STDIO_ERROR: os/stdin-read: a stream needs a key`; the MCP line loop needs separate completions to avoid accumulating the 2000-step cascade budget. `orbital-core-runtime` + compiler produced-shape adapter [mechanical] — prevention verdict: native effect/emit-contract regression gate (not a program type/structure defect). Authored repair preserves plain one-read and explicit keyed streaming, defers keyed one-read without onMessage, and adds paired route/shape controls; acceptance still pending native tests and 2100-message MCP session plus byte-fragment/ACK/EOF probes.
